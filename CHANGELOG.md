# Changelog

All notable changes to Flowerly OS are documented here. The format follows the
spirit of Keep a Changelog, and versions use semantic-ish pre-1.0 numbering.

## Unreleased

- `agenticctl` gains `goal child`, `generation promote --reason` and
  `ownership inspect|claim|release` for operations the daemon already
  implemented but the CLI could not reach. Admin commands remain enforced by
  the daemon (kernel-attested admin group, audited with the given reason).
  Covered by `check-cli-contracts.sh` and as real users in
  `test-user-ownership.py --cross-uid`.
- `distro-builder manifest check` and `manifest verify-cache` implement the
  Generation input manifest format proposed in ADR-0020 (#49): schema
  `flowerly.generation-inputs.v1`, canonical sorted-key JSON whose file
  SHA-256 is the manifest identity, dated-snapshot sources only, strict
  pacman name/version/filename validation, and an offline content-addressed
  cache check that reports every missing or tampered archive and signature
  and fails closed. Package signature trust is **not** verified yet
  (`signature_trust: not_verified`); no real Arch package set is frozen.
- `distro-builder manifest verify-cache --keyring <file>` checks every
  detached package signature with `gpgv` against the supplied keyring and
  requires the manifest's signer fingerprint (#49). Which keyring to trust
  remains an open policy decision.

## 0.0.4 — Flows and Sessions (2026-10-28)

Published as annotated tag `v0.0.4` on `master`
`b13ce02b0eb1fd88471b17b8dc60a7ea962c630c`.
[Release notes](https://github.com/Doldas/flowerly_os/releases/tag/v0.0.4) ·
[release workflow](https://github.com/Doldas/flowerly_os/actions/runs/40753771279).

Known limitations: the shipped systemd unit has no `Delegate=`, so PTY spawning
stays disabled by default. The Cargo workspace version remains `0.0.1` and the
binaries self-report `0.0.1`; this release is identified by the tag.

### Distribution-first architecture transition

- Unified Flowerly state handlers under `src/flowerlyd` with bounded Tokio work queues.
- Combined types, SQLite migrations and IPC framing in `flowerly-core`.
- Isolated `evolutiond` and distribution-oriented `distro/`, `tools/`, `testbed/`, `web-docs/` layouts.
- Updated CLI socket routing, systemd unit scaffolds and input validation.
- KVM execution and bootable images remain unimplemented.
- Storage failures now map to IPC error codes through one shared classifier (#62). SQLite UNIQUE/PRIMARY KEY failures now return `conflict` and FOREIGN KEY failures `invalid_argument` in every service; they previously returned `internal` everywhere except Generation. Only BUSY/LOCKED returns `unavailable`.
- `provider.register` refuses a non-string `kind` (it was silently registered as `local-unix`) and non-string `capabilities` entries (they were silently dropped) (#53).
- PTY writer-lease rules (exclusivity, 60 s expiry, renewal, revoked and forged tokens) are factored into pure functions with deterministic expiry tests; the same-UID isolation limits are documented (#73).
- **Safe rollback:** `flowerlyd` and every other `Store::migrate` caller now refuse to open a database migrated by a newer binary, with a message naming both schema versions. They exit before changing anything instead of running on tables they do not know. The 0.0.3 binary on a 0.0.4 database fails closed only by accident of a trigger. `releases.md` documents the verified upgrade (schema 8 → 13, data kept) and the rollback by restoring a SQLite backup.
- **PTY containment evidence (#72):** new `scripts/test-pty-containment-adversarial.py` runs the real `flowerlyd` with delegated cgroup v2 and a distinct shell UID in the Arch guest. It covers namespace escape attempts (direct, user namespace, user+mount+cgroup namespace, `setns` into PID 1); double detach/terminate; a decoy with the exited shell's exact PID (root helper `pty-pid-reuse-helper.py`) surviving stale commands, reconcile and restart; a fork bomb, a memory hog, CPU spinners and an output flood, with the daemon responsive throughout; orphans and zombies, including automatic cleanup 20 s after a natural exit; and fail-closed spawning without the `pids` controller. No containment defect was found. `pty-descendant-containment.md` records the evidence and the remaining limits, including that the shipped unit keeps PTY spawning disabled.
- **PTY crash recovery (#74):** every `session.spawn`, keyed or not, is now recorded durably before the guardian starts. Restart recovery could not find the cgroup of an unkeyed spawn whose daemon, guardian and cleanup watcher all died before its Session row committed, which left a live setsid descendant running. Recovery also removes the empty `management-*` cgroups that earlier instances left on every restart. The `session.spawn` idempotency policy is documented in one place: at-most-once admission, never expiring, no replay, lookup for reconciliation. New `scripts/test-pty-daemon-recovery.py` runs the real `flowerlyd` with delegated cgroup v2 in the Arch guest and covers daemon SIGKILL, SIGKILL before the Session row behind a real SQLite lock, total supervision loss, and concurrent duplicate keys.
- **Security (#187):** every workflow now declares a write-free top-level `permissions:` block; `project-sync.yml` and `project-sync-manual.yml` had none (Scorecard alerts 92, 93). `docs-pages.yml` grants `pages` and `id-token: write` only to the jobs that publish. New `scripts/test-workflow-permissions.py` (CI, with regression tests) fails on a missing or writable top-level block and on any job-level write scope not recorded with its reason. `security-alert-triage.md` documents each remaining alert with Scorecard's evidence, its impact and its disposition; none is dismissed.
- **Security (#240):** the shipped `flowerlyd.service` and the multi-user drop-in now also unset `FLOWERLY_PTY_ISOLATION` and `FLOWERLY_PTY_CGROUP_ROOT`. The unit has no `Delegate=`, so PTY spawning is disabled. A manager-injected `FLOWERLY_PTY_ISOLATION=development` (`systemctl set-environment`, `DefaultEnvironment=`) would have turned that into PTY spawning without cgroup containment. `flowerlyd` now warns whenever development isolation is active. Direct development runs are unchanged.
- **Security (#237):** the shipped `flowerlyd.service` and the multi-user drop-in now unset `AGENTIC_DATABASE_PATH`. Through the service manager's environment (`systemctl set-environment`, `DefaultEnvironment=` or a stale drop-in), it could repoint the system database to `/dev/shm`, `/run/flowerly` or a second file under `/var/lib/flowerly`, even with `ProtectSystem=strict`. The daemon then started silently on an empty or volatile database, without the users' data, ownership or `admin_audit` history. `flowerlyd` now logs the effective database and warns when it is not `<state_dir>/state.db`. Direct test and recovery runs of the binary are unchanged.
- **Opt-in multi-user access (#225 PR 8).** Per-user ownership is complete, so an administrator may now admit `flowerly-users` members by installing the maintained drop-in `/usr/share/flowerly/systemd/flowerlyd-multi-user.conf` as `/etc/systemd/system/flowerlyd.service.d/50-multi-user.conf`. The drop-in sets primary group `flowerly-users` (socket 0660), `/run/flowerly` 0750 and the users group. The state stays 0700/0600. **The shipped default stays service-account-only** and the drop-in is staged inactive. Removing it and restarting is the rollback, and data is kept. `flowerlyd` still refuses a users group while any User command is not owner-scoped, now with no override: the test-only `AGENTIC_TEST_ONLY_UNENFORCED_OWNERSHIP` acknowledgment is removed and ignored. Administration uses a human account in both `flowerly-users` and `flowerly-admin`, journaled and audited by its own uid. The temporary break-glass procedure is no longer supported. PTY commands stay limited to the service account. New `scripts/test-systemd-multi-user.py` accepts the default, opt-in and disabled configurations with real systemd, in the Arch guest and on PR runners. The Arch guest also runs both cross-UID suites, and a `workflow_dispatch` of `ci` runs the Arch guest acceptance on any branch head. **Upgrade:** install the new unit and drop-in file; remove any local drop-in that set the test-only variable.
- **Ownership administration (#225 PR 7).** New audited Admin commands `ownership.inspect {ref, reason}`, `ownership.claim {ref, to_uid, reason, expect}` and `ownership.release {ref, reason, expect}` handle legacy `unresolved` data. Ownership moves as a whole same-owner component: the object and everything linked to it by a same-owner reference (Goal tree, Executions, Sessions in a Flow, Generation reason and parent, workload profile, usage). `system` objects such as General never move. Another owner's linked object blocks the move, and `expect` must match the component size. Every moved object gets an append-only `admin_audit` row (admin uid, object, previous and new owner, reason) in the same transaction, and inspect is audited too. Inspect returns ownership metadata only, never content. There is no migration. The shipped unit stays service-account-only until #225 PR 8.
- **Ownership enforcement (#225 PR 6): Generations and audited promotion.** Generation candidates are private to their creator: `generation.list`/`inspect` show the caller's own and `system` Generations, and another user's or a legacy `unresolved` candidate is `not_found`. `generation.create` accepts only a visible `parent` (migration 0013 trigger). New Admin command `generation.promote {id, reason}` makes a candidate a shared `system` Generation in one transaction with an append-only `admin_audit` record (admin uid, object, previous and new owner, reason). A promoted Generation never reveals its reason Goal to anyone but the Goal's owner. **Behavior change:** `generation.activate` refuses a Generation that is not `system` (`conflict`; promote it first). Every User command is now owner-scoped, but `flowerlyd` still refuses a users group until multi-user admission is explicitly restored after acceptance (#225 PR 8); the shipped unit stays service-account-only.
- **Ownership enforcement (#225 PR 5): Compute.** AI profiles are private to their owner; `system` profiles are shared read-only (editing or renaming one is `permission_denied`). Profile names are unique per owner instead of globally, so a name clash no longer reveals another user's profile (migration 0012). A profile `base` resolves to the owner's own profile first, then a `system` one, and never to another user's. Workloads and usage are private: `workload.submit` accepts only a visible profile, `workload.show`/`stop`/`complete` and `inference.request` answer another user's workload like a missing one, and usage totals count only the caller's own usage. Database triggers keep workloads with a visible profile and usage with its workload's owner. **Behavior change:** `workload.list` with `"mine": false` now returns `invalid_argument` instead of listing every user's workloads. **Fix:** PR 4 classified workload provenance endpoints by the wrong id prefix, so the `provider → workload` edge recorded by `inference.request` was visible to every user; it is now visible only to the workload owner. Generation listings are not yet owner-scoped (PR 6), so the shipped unit stays service-account-only.
- **Ownership enforcement (#225 PR 4): provenance and Status.** `provenance.from`/`provenance.to` return an edge only when both of its endpoints are visible to the caller. Visible means the caller's own object, General or a `system` record, a catalog model or provider, or the caller's own actor label. An edge to another user's object is hidden, and an edge between two endpoints with no owner yet is never shown. Querying another user's object returns no edges, like a missing reference. Status counts are now fully per caller: generations, profiles and active workloads count own + `system`, provenance counts visible edges, and models and providers stay shared catalog counts. `generation.create` accepts only the caller's own `reason_goal` (migration 0011 adds a database trigger as well), and `generation.inspect` hides another user's reason Goal. The shipped unit stays service-account-only until PRs 5–6.
- **Ownership enforcement (#225 PR 3): Flows, Goals, Sessions and Executions are private to their kernel-attested owner.** Each command takes the caller explicitly, and the owner filter runs inside the same SQLite statement or transaction as the mutation. Another user's object is `not_found`, exactly like a missing one. Cross-object references (child Goal, Execution Goal, Session Flow) must have the same owner, also enforced by database triggers. Status counts and the new `foreground_flow` are per caller. **Per-user foreground:** migration 0010 adds `flow_foreground`, one row per uid, where no row means General. Activating General or any Flow never changes another user's foreground. `FOREGROUND` is no longer a Flow lifecycle state; `flow.list`/`activate`/`archive` return `state` plus a separate `foreground` flag. The single-foreground index is dropped in the same atomic migration. Provenance, Generations and Compute are not yet owner-scoped, so the shipped unit stays service-account-only. **Upgrade:** back up `state.db`; there is no down-migration. A legacy foreground goes to its owner, if resolved, or otherwise becomes General.
- **Security (#225):** `flowerlyd` refuses to start when a users group is configured (environment, drop-in or config file) until per-user ownership is enforced. A stale local drop-in can therefore no longer silently re-admit `flowerly-users` members. Only the exact test-only acknowledgment `AGENTIC_TEST_ONLY_UNENFORCED_OWNERSHIP=members-can-read-each-others-data` overrides it, for the cross-UID tests. The shipped unit unsets it, and the offline admission check rejects it. **Upgrade:** if `flowerlyd` fails with a #225 error, remove the local `AGENTIC_USERS_GROUP`/`users_group` override.
- **Ownership recording (#225 PR 2, not yet enforced):** migration 0009 adds `owner_class`/`owner_uid` to flows, goals, sessions, executions, generations, profiles, providers, workloads and usage. The kernel-attested caller is passed explicitly through the Router and worker queues, every create path records it as owner, and `created_by` stays audit text. Legacy and malformed owners are `unresolved` and protected; a missing owner fails closed. Reads are not filtered yet, so the shipped unit stays service-account-only. The shipped unit also unsets `AGENTIC_USERS_GROUP` and `AGENTIC_CONFIG` so the service manager cannot inject them. Unused duplicate compute handlers were removed. **Upgrade:** back up `state.db` first; there is no down-migration.
- `flowerlyd` journals one `admin command` record (target `flowerly::admin_audit`) per Admin decision and IPC `shutdown`: command, peer uid/gid/pid, `service_account` and outcome, never arguments. The break-glass maintenance procedure documents that IPC sees the service account, so the operator is identified by the `sudo` journal record (#225).
- **Security (#225):** the shipped `flowerlyd` unit is temporarily service-account-only. It no longer sets `AGENTIC_USERS_GROUP`; `Group=flowerly` and `RuntimeDirectoryMode=0700` keep the socket private, because `flowerly-users` members could read and change each other's data. Admin group membership alone no longer admits a different-UID peer. Admin commands stay denied by default; a root-only out-of-band procedure is documented. A new offline check rejects any shipped configuration that re-enables admission.
- Compute idempotency and silent-default fixes from the #53 audit. A retried `profile.clone` or `provider.register` with the same `operation_id` now returns the stored object instead of a never-created id, and a reused key with other arguments is `conflict`. `profile.edit` honors `operation_id` instead of appending a duplicate version. `usage.record` refuses `operation_id` instead of ignoring it, and `profile.rename` validates it. `workload.list` accepts `"mine": null`. `inference.request` no longer assumes the `ask` fallback for an unresolvable profile, or records a missing provider latency as zero.
- `flowerlyd` enforces administrative authorization by Linux group (#31). Admin commands and IPC `shutdown` require kernel-verified membership of `AGENTIC_ADMIN_GROUP` (`SO_PEERCRED` plus `SO_PEERGROUPS`); with no admin group they are refused for everyone, including the service account. `AGENTIC_USERS_GROUP` members may connect (socket mode 0660) and run User commands. PTY commands are limited to the service account. An unknown group stops startup. The systemd unit uses `flowerly-users` and `flowerly-admin`. **Upgrade:** add administrators to `flowerly-admin`, or Admin commands stay refused.
- Every `flowerlyd` command is classified User or Admin in one inventory, and the router dispatches only classified commands. Status reports the transitional `admin_authorization` policy (#31).
- PTY caller mistakes (cursor past the end or negative, malformed `wait_ms`, write data or dimensions) now return `invalid_argument` instead of retryable `unavailable`. The long-poll contract is covered by a new adversarial test (#73).
- Session metadata commands use typed IPC v1 arguments: a non-string `kind` no longer silently becomes `local-pty`, and a non-string `cwd` is no longer dropped (#53).
- Flow and Goal commands use typed IPC v1 arguments: wrongly typed known fields return `invalid_argument` (for example, a non-string Goal `rationale` is no longer silently dropped), `null` means absent, and unknown fields are ignored (#53).
- `flowerlyd` Status reports `ready: true` only after the database answers one consistent count snapshot, which now includes `provenance_edge_count`. A failed read now reports `ready: false` with a typed `error_code` (#31).
- IPC servers hold an exclusive per-socket instance lock (`<socket>.lock`) and automatically recover a socket left by a crashed instance only after verifying it is stale. A second live instance is refused (#31).
- IPC deadline errors say whether the request was never executed (queued) or has an unknown outcome (handler running), with elapsed milliseconds. Every request logs a structured `ipc request` event with queue, handler and total time (#62).


### Added

- Rust Cargo workspace with the shared `flowerly-core` crate.
- Typed, prefixed, UUID-backed identifiers and durable domain models
  (Flow, Goal, Session, Execution, Generation, ProvenanceEdge, and others).
- SQLite-backed storage with an ordered, idempotent migration runner and the
  initial schema (`migrations/0001_init.sql`).
- Unix-domain-socket, length-prefixed JSON IPC (protocol v1).
- Shared daemon foundations: `ServiceConfig`, structured tracing, and
  `run_service` with SIGTERM and IPC shutdown.
- Unified `flowerlyd` for Flow, Goal, Session, Generation, Provenance,
  Capability, Compute and Execution modules; separate `evolutiond` boundary.
- The `agenticctl` control-plane CLI.
- Root documentation and architecture guides under `web-docs/docs/`.
